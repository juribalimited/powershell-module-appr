Examples Guide

The Juriba.AppR/Examples/ folder contains working scripts that demonstrate every major automation pattern supported by the module. There are PowerShell scripts for server-side automation, a Node.js script for JavaScript-based workflows, and HTML self-service portals for browser-based packaging. Each example is self-contained and can be run directly after configuring connection parameters.

PowerShell Examples

Test-QuickStart.ps1

A comprehensive validation script that exercises every read-only cmdlet in the module, then optionally runs the full upload-and-create workflow. Use this to confirm the module works end-to-end against a live instance.

What it tests

  • Connection and disconnection (Connect-JuribaAppR, Disconnect-JuribaAppR)
  • Instance info, user identity, application list, application detail, events, packages, package detail, and status tracking
  • VM groups, integration connectors, generic integrations, Knowledge Base search, and test applications
  • Upload and create workflow (unless -SkipUpload is specified)

Parameters

ParameterRequiredDescription
-InstanceUrlYesBase URL of the App Readiness instance
-APIKeyYesAPI key for authentication
-SetupFilePathNoPath to a setup file. If omitted, a small dummy MSI is created for testing.
-SkipUploadNoSwitch. When specified, skips the upload/create test and only validates read-only cmdlets.

How to run

# Full test (read-only + upload)
.\Test-QuickStart.ps1 -InstanceUrl "https://demo.appr.juriba.app" -APIKey "your-key"

# With a real installer
.\Test-QuickStart.ps1 -InstanceUrl "https://demo.appr.juriba.app" -APIKey "your-key" `
    -SetupFilePath "C:\Installers\Firefox-Setup.exe"

# Read-only tests only
.\Test-QuickStart.ps1 -InstanceUrl "https://demo.appr.juriba.app" -APIKey "your-key" -SkipUpload

Expected output

Each cmdlet is tested individually and reported as PASSED or FAILED. At the end, a summary table shows the total count with details for any failures. When the upload test runs, it reports the UUID, extracted metadata, and creation response.

Test-UploadAndWatch.ps1

The primary automation use case: upload an installer, create the application with -RunImmediately, and poll until packaging completes. The script handles metadata extraction, VM group selection, and status monitoring automatically.

Parameters

ParameterRequiredDescription
-InstanceUrlNoBase URL. Not required if already connected via Connect-JuribaAppR.
-APIKeyNoAPI key. Not required if already connected.
-SetupFilePathYesPath to the installer to upload (EXE, MSI, etc.).
-IntervalSecondsNoSeconds between status polls. Default: 300 (5 minutes).
-TimeoutMinutesNoMaximum minutes to wait for packaging. Default: 30.

The 5 steps

  1. Connect -- skips if a session already exists, otherwise requires -InstanceUrl and -APIKey.
  2. Upload -- sends the file in chunks, reports UUID and extracted PE metadata (ProductName, CompanyName, ProductVersion).
  3. Create application -- submits with -RunImmediately. The cmdlet reads Default Settings automatically. Command lines are determined server-side.
  4. Wait for app ID -- polls Get-JuribaAppRApplicationCreationState every 10 seconds (5-minute timeout). Falls back to searching the application list by name if the creation state endpoint does not resolve.
  5. Watch status -- polls Watch-JuribaAppRApplicationStatus at the configured interval until ReadyForQualityReview or a failure state.

Failure diagnostics

When packaging fails or is cancelled, the script automatically dumps: ext.status, ext.progressPercent, ext.statusMessage, ext.errorMessage, per-package status and errors, and the full application event history. Use -Verbose for additional detail during upload and creation.

How to run

# Standard usage
.\Test-UploadAndWatch.ps1 -InstanceUrl "https://demo.appr.juriba.app" `
    -APIKey "your-key" -SetupFilePath "C:\Installers\7z2407-x64.exe"

# Already connected, with faster polling
.\Test-UploadAndWatch.ps1 -SetupFilePath "C:\Installers\Firefox.exe" `
    -IntervalSeconds 60 -TimeoutMinutes 60

# With verbose output
.\Test-UploadAndWatch.ps1 -InstanceUrl "https://demo.appr.juriba.app" `
    -APIKey "your-key" -SetupFilePath "C:\Installers\app.msi" -Verbose

Test-KBSearchAndPackage.ps1

Demonstrates the Knowledge Base workflow: search for an application by name, interactively select a version and architecture, download the installer from the KB, and package it.

Parameters

ParameterRequiredDescription
-InstanceUrlYesBase URL of the App Readiness instance.
-APIKeyYesAPI key for authentication.
-SearchTermYesApplication name to search for in the Knowledge Base.
-IntervalSecondsNoSeconds between status polls. Default: 60.
-TimeoutMinutesNoMaximum minutes to wait. Default: 30.

Interactive flow

The script presents numbered menus at each decision point:

  1. Search results -- lists matching applications with vendor names. Auto-selects if only one result.
  2. Version selection -- shows the five most recent versions, sorted descending. Defaults to the latest.
  3. Architecture selection -- lists available sources for the chosen version with architecture labels (x86/x64). Defaults to the first x64 EXE if available.

After selection, the script downloads the setup file to a temporary directory, uploads it, creates the application with KB metadata as hints, and watches packaging to completion.

How to run

.\Test-KBSearchAndPackage.ps1 -InstanceUrl "https://demo.appr.juriba.app" `
    -APIKey "your-key" -SearchTerm "7-Zip"

Test-WatchAndPublishIntune.ps1

A long-running watcher that polls for applications with IntuneWin packages that have passed smoke testing and automatically publishes them to Microsoft Intune. Designed to run as a scheduled task or background job.

Parameters

ParameterRequiredDescription
-InstanceUrlYesBase URL of the App Readiness instance.
-APIKeyYesAPI key for authentication.
-TargetStatusesNoWorkflow statuses to consider. Default: Ready for UAT, Ready for Publishing.
-AllowAmberNoSwitch. When set, apps with amber (warnings) test results are also published. Default: green only.
-IntervalSecondsNoSeconds between poll cycles. Default: 300.
-TimeoutMinutesNoMaximum run time. Default: 0 (run indefinitely).
-DryRunNoSwitch. Identifies qualifying apps without publishing them.

Polling loop and deduplication

Each poll cycle retrieves all applications via Get-JuribaAppRApplicationList -AllUsers -Lite, filters to the target statuses, and skips any app already in the published-apps hashtable. For each candidate, it calls Get-JuribaAppRTestResult to check IntuneWin smoke test results (packageType 4). RAG status values are: 1 = green (pass), 2 = amber (warnings), 3 = red (fail). Only apps meeting the threshold are published.

How to run

# Dry run — see what would be published
.\Test-WatchAndPublishIntune.ps1 -InstanceUrl "https://demo.appr.juriba.app" `
    -APIKey "your-key" -DryRun

# Live, with amber results accepted, polling every 60 seconds
.\Test-WatchAndPublishIntune.ps1 -InstanceUrl "https://demo.appr.juriba.app" `
    -APIKey "your-key" -AllowAmber -IntervalSeconds 60

# Run for 2 hours then stop
.\Test-WatchAndPublishIntune.ps1 -InstanceUrl "https://demo.appr.juriba.app" `
    -APIKey "your-key" -TimeoutMinutes 120

Export-MSIXAppAttachToShare.ps1

Downloads MSIX App Attach (or other package types) from a Generic Integration and copies them to an SMB file share. Designed for organizations distributing packages to Azure Virtual Desktop or Windows 365 environments.

Parameters

ParameterRequiredDescription
-InstanceUrlYesBase URL of the App Readiness instance.
-SecretNameYes*Name of the secret in SecretManagement containing the API key. Use Set-JuribaAppRAPIKey to store. Mutually exclusive with -APIKey.
-APIKeyYes*API key as plain text. Mutually exclusive with -SecretName.
-IntegrationIdNoID of the Generic Integration to pull from. If omitted, lists all integrations (auto-selects if only one exists).
-SMBSharePathYesUNC path to the SMB share (e.g., \\fileserver\msix-packages).
-StagingPathNoLocal staging directory for downloads. Defaults to a timestamped temp directory.
-PackageTypesNoPackage types to download. Default: AppAtach. Other options: Msix, Msi, AppV, IntuneWin, Psadt.
-LimitNoMaximum publishing records to process. Default: 50.

* One of -SecretName or -APIKey is required.

The download-copy-log-update cycle

For each publishing record, the script: (1) retrieves publishing properties for display, (2) downloads the package source to the staging directory, (3) copies it to the SMB share, (4) logs success via Add-JuribaAppRGenericIntegrationLog, and (5) updates the publishing state to Succeeded. On error, it logs the failure and sets the state to Failed. After all records are processed, the staging directory is cleaned up automatically (if it was auto-created).

Pester tests

A companion Pester test file, Export-MSIXAppAttachToShare.Tests.ps1, is provided for validating the script's behavior with mocked cmdlets.

How to run

# Using SecretManagement (preferred for automation)
.\Export-MSIXAppAttachToShare.ps1 `
    -InstanceUrl "https://appr.example.com" `
    -SecretName "AppR-Production" `
    -IntegrationId 3 `
    -SMBSharePath "\\fileserver\msix-appattach"

# Using API key, downloading both MSIX and App Attach
.\Export-MSIXAppAttachToShare.ps1 `
    -InstanceUrl "https://appr.example.com" `
    -APIKey "your-key" `
    -SMBSharePath "\\avd-share\packages" `
    -PackageTypes "MsixAppAttach,Msix"

# With custom staging and higher limit
.\Export-MSIXAppAttachToShare.ps1 `
    -InstanceUrl "https://appr.example.com" `
    -SecretName "AppR-Production" `
    -SMBSharePath "\\share\packages" `
    -StagingPath "D:\Staging" `
    -Limit 200

JavaScript Example

appr-upload-and-watch.js

A single-file Node.js script (no external dependencies) that performs the full upload, create, and watch workflow. It uses only built-in Node.js modules (fs, path, crypto) and the native fetch API (requires Node.js 18+).

What it does

  1. Validates the API key by calling the package types matrix endpoint.
  2. Reads Default Settings to determine VM groups and output format bitmask.
  3. Resolves the current user ID for upload attribution.
  4. Uploads the setup file in 2 MB chunks using Dropzone.js-compatible multipart form data.
  5. Extracts metadata via server-side PE analysis, with client-side FileVersionInfo and filename as fallbacks.
  6. Gets install command suggestions using the same priority logic as the PowerShell module (KB > Programmatic > AI).
  7. Creates the application and polls until packaging completes or fails.

Environment variables

VariableRequiredDescription
APPR_API_KEYYesAPI key for authentication. Do not hardcode in the script.
APPR_INSTANCENoInstance URL. Defaults to https://demo.appr.juriba.app.

How to run

# Set the API key (Windows cmd)
set APPR_API_KEY=your-key-here

# Set the API key (PowerShell)
$env:APPR_API_KEY = "your-key-here"

# Run with a file path argument
node appr-upload-and-watch.js "C:\Installers\TeamViewer_Setup_x64.exe"

# Or set APPR_INSTANCE for a different environment
set APPR_INSTANCE=https://appr.example.com
node appr-upload-and-watch.js "C:\Installers\app.msi"

HTML Self-Service Portals

appr-self-service.html

A browser-based self-service portal that provides two packaging workflows: Knowledge Base search (find and package a known application) and local file upload (upload an installer from the user's machine). The portal connects directly to the App Readiness API using the instance URL and API key entered in the browser.

When a CORS proxy is available (see appr-self-service.js below), the portal can also download KB installers and extract PE metadata client-side. Without the proxy, it falls back to direct API calls for instances that allow cross-origin requests.

appr-self-service-with-testing-visibility.html

An extended version of the self-service portal that adds live smoke test monitoring. After an application is created, this variant polls for test results and displays the RAG status (green/amber/red) in real time. Use this when end users need visibility into whether their submitted application passed automated testing.

appr-self-service.js

A lightweight Node.js proxy server that enables the HTML self-service portals to work without CORS issues. Browser-based JavaScript cannot call the App Readiness API directly from a different origin, so this proxy relays API requests and adds the required CORS headers.

Why it exists

The App Readiness API does not serve CORS headers, which means browsers block cross-origin requests from the HTML portals. The proxy server accepts requests from the browser, forwards them to the App Readiness instance, and returns the responses with permissive CORS headers.

URLs it exposes

URLDescription
http://localhost:3000/Serves the standard self-service portal (appr-self-service.html).
http://localhost:3000/testingServes the testing-visibility variant.
http://localhost:3000/healthHealth check endpoint. Returns {"ok":true}.
http://localhost:3000/download?url=...Downloads a KB file (bypasses vendor CDN CORS restrictions).
http://localhost:3000/metadata?name=file.exePOST endpoint. Accepts raw file bytes and extracts PE metadata via PowerShell FileVersionInfo.
http://localhost:3000/proxy/{base64_instance}/api/...Proxies any API call to the App Readiness instance (base64-encoded URL in the path).

How to run

# Start the proxy server (requires Node.js 18+)
node appr-self-service.js

# The server prints:
#   http://localhost:3000/          Standard portal
#   http://localhost:3000/testing   With smoke test monitoring

# To use a custom port:
PORT=8080 node appr-self-service.js

Once the proxy is running, open http://localhost:3000 in a browser, enter the App Readiness instance URL and API key, and use the portal to search the Knowledge Base or upload local installers.
