Workflows

This page walks through five end-to-end workflows that combine multiple cmdlets into practical automation patterns. Each workflow references a working example script shipped in the Juriba.AppR/Examples/ folder. A sixth section covers the key internal behaviors that affect every workflow.

1. Upload and Package

The most common automation scenario: upload an installer, create the application, and wait for packaging to finish. This maps directly to the Test-UploadAndWatch.ps1 example script.

Steps

  1. Connect to the App Readiness instance.
  2. Upload the setup file in chunks via Send-JuribaAppRSetupFile. The cmdlet returns a UUID, file metadata, and any client-side PE metadata it can extract.
  3. Create the application with New-JuribaAppRApplication -RunImmediately. The cmdlet automatically reads Default Settings (VM groups, output format bitmask), calls server-side metadata extraction, and submits the packaging job. Command lines are determined server-side, not sent in the payload.
  4. Wait for the application ID. Creation is asynchronous. Poll Get-JuribaAppRApplicationCreationState until the server assigns an ID.
  5. Watch status with Watch-JuribaAppRApplicationStatus until the application reaches ReadyForQualityReview (or a failure state).

Complete Script

# Upload and Package — end-to-end workflow
# Reference: Juriba.AppR/Examples/Test-UploadAndWatch.ps1

# 1. Connect (skip if already connected)
Connect-JuribaAppR -Instance "https://demo.appr.juriba.app" -APIKey $apiKey

# 2. Upload the installer
$upload = Send-JuribaAppRSetupFile -FilePath "C:\Installers\7z2407-x64.exe" -Verbose
# Returns: Uuid, FileName, FileSize, TotalChunks, ProductName, CompanyName, ProductVersion

# 3. Create the application — New-JuribaAppRApplication handles:
#    - Reading Default Settings (VM groups, output format bitmask)
#    - Server-side metadata extraction (name, manufacturer, version)
#    - Command lines are NOT sent; the server determines them via
#      hash matching, Juriba KB, and AI-based detection
$splatCreate = @{
    Uuid           = $upload.Uuid
    FileName       = $upload.FileName
    FileSize       = $upload.FileSize
    TotalChunks    = $upload.TotalChunks
    RunImmediately = $true
}
# Pass client-side metadata as fallback hints
if ($upload.ProductName)    { $splatCreate['Name']         = $upload.ProductName }
if ($upload.CompanyName)    { $splatCreate['Manufacturer'] = $upload.CompanyName }
if ($upload.ProductVersion) { $splatCreate['Version']      = $upload.ProductVersion }

$app = New-JuribaAppRApplication @splatCreate -Verbose

# 4. Wait for creation to resolve (server assigns the app ID asynchronously)
$appId = $null
$creationTimeout = (Get-Date).AddMinutes(5)
while ((Get-Date) -lt $creationTimeout) {
    $state = Get-JuribaAppRApplicationCreationState -UploadId $upload.Uuid
    $resolvedId = $state.data.applicationId
    if ($resolvedId -and $resolvedId -gt 0) {
        $appId = $resolvedId
        break
    }
    Start-Sleep -Seconds 10
}

# 5. Watch packaging status until ReadyForQualityReview or failure
$result = Watch-JuribaAppRApplicationStatus -AppId $appId `
    -IntervalSeconds 300 -TimeoutMinutes 30
Write-Host "Status: $($result.Status)  Progress: $($result.Progress)%"

On failure, the script dumps diagnostics including ext.status, ext.errorMessage, package details, and the application event history. See Test-UploadAndWatch.ps1 for the full failure-diagnostics block.

2. Knowledge Base Search and Package

Instead of uploading a local installer, search the Juriba Knowledge Base for a known application, download it, and package it. This maps to Test-KBSearchAndPackage.ps1.

Steps

  1. Connect to the instance.
  2. Search the KB with Search-JuribaAppRKnowledgeBase -Search "7-Zip". Returns matching applications with vendor names.
  3. Pick an application from the results.
  4. Get versions and sources by calling Search-JuribaAppRKnowledgeBase -ApplicationId $id. This returns all available versions, architectures, and download URLs.
  5. Download the setup file from the KB download URL to a local staging directory.
  6. Upload via Send-JuribaAppRSetupFile.
  7. Create with New-JuribaAppRApplication -RunImmediately, passing KB metadata (product name, vendor, version) as hints.
  8. Wait for the app ID and watch packaging status as in the Upload and Package workflow.

Complete Script

# Knowledge Base Search and Package
# Reference: Juriba.AppR/Examples/Test-KBSearchAndPackage.ps1

Connect-JuribaAppR -Instance "https://demo.appr.juriba.app" -APIKey $apiKey

# Search the Knowledge Base
$kbResults = Search-JuribaAppRKnowledgeBase -Search "7-Zip"
# Returns: applicationId, applicationName, vendorName for each match

# Get versions for a specific application
$sources = Search-JuribaAppRKnowledgeBase -ApplicationId $kbResults[0].applicationId
# Returns: version, architecture (32/64), fileName, downloadUrl for each source

# Pick the latest x64 version
$src = $sources | Where-Object { $_.architecture -eq 64 } |
    Sort-Object { [version]($_.version -replace '[^0-9.]', '') } -Descending |
    Select-Object -First 1

# Download the setup file from the KB
$localPath = Join-Path $env:TEMP $src.fileName
Invoke-WebRequest -Uri $src.downloadUrl -OutFile $localPath

# Upload to App Readiness
$upload = Send-JuribaAppRSetupFile -FilePath $localPath -Verbose

# Create with KB metadata as hints
$splatCreate = @{
    Uuid           = $upload.Uuid
    FileName       = $upload.FileName
    FileSize       = $upload.FileSize
    TotalChunks    = $upload.TotalChunks
    RunImmediately = $true
}
if ($src.productName) { $splatCreate['Name']         = $src.productName }
if ($src.vendor)      { $splatCreate['Manufacturer'] = $src.vendor }
if ($src.version)     { $splatCreate['Version']      = $src.version }

$app = New-JuribaAppRApplication @splatCreate -Verbose

# Wait for app ID, then watch packaging
$appId = $null
$timeout = (Get-Date).AddMinutes(5)
while ((Get-Date) -lt $timeout) {
    $state = Get-JuribaAppRApplicationCreationState -UploadId $upload.Uuid
    if ($state.data.applicationId -gt 0) { $appId = $state.data.applicationId; break }
    Start-Sleep -Seconds 10
}

$result = Watch-JuribaAppRApplicationStatus -AppId $appId `
    -IntervalSeconds 60 -TimeoutMinutes 30

3. Automated Publish to Intune

A long-running watcher that polls for applications ready to publish, verifies their smoke test results, and automatically publishes qualifying IntuneWin packages to Microsoft Intune. This maps to Test-WatchAndPublishIntune.ps1.

Steps

  1. Connect to the instance.
  2. Poll the application list on an interval, filtering for apps in a publishable workflow state (ReadyForUat, ReadyForPublishing, or custom).
  3. Check smoke test results via Get-JuribaAppRTestResult. Only green (clean pass) results qualify by default; the -AllowAmber switch adds amber (pass with warnings).
  4. Publish qualifying apps via Invoke-JuribaAppRPublishIntune.
  5. Track published apps in a hashtable to prevent duplicate publishing across poll cycles.

Complete Script

# Automated Publish to Intune
# Reference: Juriba.AppR/Examples/Test-WatchAndPublishIntune.ps1

Connect-JuribaAppR -Instance "https://demo.appr.juriba.app" -APIKey $apiKey

$publishedAppIds = @{}                           # Deduplication tracker
$targetStatuses  = @('Ready for UAT', 'Ready for Publishing')
$acceptableRAG   = @(1)                          # 1=green; add 2 for amber

while ($true) {
    # Get all applications in a publishable state
    $allApps    = Get-JuribaAppRApplicationList -AllUsers -Lite
    $candidates = @($allApps | Where-Object {
        $targetStatuses -contains $_.status -and
        -not $publishedAppIds.ContainsKey($_.id)
    })

    foreach ($app in $candidates) {
        # Check smoke test results for the IntuneWin package (packageType 4)
        $testResults = Get-JuribaAppRTestResult -AppId $app.id
        $intuneTests = @($testResults | Where-Object { $_.typeOfPackage -eq 4 })
        if ($intuneTests.Count -eq 0) { continue }

        # Look for a completed test with an acceptable RAG status
        $passed = $false
        foreach ($test in $intuneTests) {
            foreach ($eg in $test.evergreenInformation) {
                if ($eg.complete -and $acceptableRAG -contains $eg.rAGStatus) {
                    $passed = $true; break
                }
            }
            if ($passed) { break }
        }
        if (-not $passed) { continue }

        # Publish to Intune
        Invoke-JuribaAppRPublishIntune -Body @{
            applicationId = $app.id
            packageType   = 4      # IntuneWin
        }
        $publishedAppIds[$app.id] = $true
        Write-Host "Published: $($app.name) v$($app.version)"
    }

    Start-Sleep -Seconds 300        # Poll every 5 minutes
}

The script supports a -DryRun switch that identifies qualifying apps without actually publishing them, and a -TimeoutMinutes parameter to limit how long the watcher runs.

4. Export MSIX App Attach to SMB Share

Downloads MSIX App Attach packages from a Generic Integration and copies them to an SMB file share for distribution to Azure Virtual Desktop (AVD) or Windows 365 environments. This maps to Export-MSIXAppAttachToShare.ps1.

Steps

  1. Connect to the instance (supports -SecretName for SecretManagement or -APIKey for plain text).
  2. Find the Generic Integration via Get-JuribaAppRGenericIntegration. If only one exists, it is auto-selected.
  3. List published packages using Get-JuribaAppRGenericIntegrationPublishing with the configured package types and limit.
  4. Download each package to a local staging directory via Get-JuribaAppRGenericIntegrationSource.
  5. Copy to the SMB share using Copy-Item.
  6. Log success in App Readiness via Add-JuribaAppRGenericIntegrationLog.
  7. Update the publishing state to Succeeded (or Failed on error) via Update-JuribaAppRGenericIntegrationPublishingState.
  8. Clean up the staging directory after all downloads complete.

Complete Flow

# Export MSIX App Attach to SMB Share
# Reference: Juriba.AppR/Examples/Export-MSIXAppAttachToShare.ps1

# Connect using SecretManagement (preferred for automation)
Connect-JuribaAppR -Instance "https://appr.example.com" -SecretName "AppR-Production"

# Find the Generic Integration
$integrations = Get-JuribaAppRGenericIntegration
$integrationId = $integrations[0].id

# List published MSIX App Attach packages
$publishings = Get-JuribaAppRGenericIntegrationPublishing `
    -IntegrationId $integrationId -Limit 50 -PackageTypes "AppAtach"

# Prepare staging directory
$staging = Join-Path $env:TEMP "AppR-Export-$(Get-Date -Format 'yyyyMMdd-HHmmss')"
New-Item -Path $staging -ItemType Directory | Out-Null

foreach ($pubId in $publishings) {
    try {
        # Download to staging
        $file = Get-JuribaAppRGenericIntegrationSource `
            -IntegrationId $integrationId -PublishingId $pubId -SourcePath $staging

        # Copy to SMB share
        Copy-Item -Path (Join-Path $staging $file) `
                  -Destination "\\fileserver\msix-appattach\$file" -Force

        # Log success and update state
        Add-JuribaAppRGenericIntegrationLog `
            -IntegrationId $integrationId -PublishingId $pubId `
            -Message "Exported to share" -Level "Information" -Date (Get-Date)

        Update-JuribaAppRGenericIntegrationPublishingState `
            -IntegrationId $integrationId -PublishingId $pubId `
            -PublishingState "Succeeded"
    }
    catch {
        # Log failure and update state
        Add-JuribaAppRGenericIntegrationLog `
            -IntegrationId $integrationId -PublishingId $pubId `
            -Message "Export failed: $($_.Exception.Message)" -Level "Error" -Date (Get-Date)

        Update-JuribaAppRGenericIntegrationPublishingState `
            -IntegrationId $integrationId -PublishingId $pubId `
            -PublishingState "Failed"
    }
}

# Clean up staging
Remove-Item $staging -Recurse -Force -ErrorAction SilentlyContinue
Disconnect-JuribaAppR

5. ServiceNow Integration Pattern

A conceptual pattern for integrating App Readiness with ServiceNow (or any ticketing system). The flow receives a packaging request via a ticket, drives the full lifecycle through the API, and reports the outcome back to the ticket.

Conceptual Flow

  1. Receive a ticket from ServiceNow containing the installer path and requester details.
  2. Upload the setup file.
  3. Create the application with -RunImmediately.
  4. Assign the owner from the ticket metadata.
  5. Watch until packaging reaches a terminal state.
  6. Publish to the target platform.
  7. Report status back to ServiceNow.

Script Skeleton

# ServiceNow Integration Pattern (conceptual)
# Adapt this skeleton to your ticketing system's webhook or polling mechanism.

param (
    [string]$TicketId,
    [string]$InstallerPath,
    [string]$RequesterEmail,
    [string]$TargetPlatform = "Intune"
)

# Connect
Connect-JuribaAppR -Instance $env:APPR_INSTANCE -SecretName "AppR-ServiceNow"

try {
    # Upload and create
    $upload = Send-JuribaAppRSetupFile -FilePath $InstallerPath
    $app = New-JuribaAppRApplication -Uuid $upload.Uuid `
        -FileName $upload.FileName -FileSize $upload.FileSize `
        -TotalChunks $upload.TotalChunks -RunImmediately

    # Wait for the app ID
    $appId = $null
    $timeout = (Get-Date).AddMinutes(5)
    while ((Get-Date) -lt $timeout) {
        $state = Get-JuribaAppRApplicationCreationState -UploadId $upload.Uuid
        if ($state.data.applicationId -gt 0) {
            $appId = $state.data.applicationId
            break
        }
        Start-Sleep -Seconds 10
    }

    # Assign owner from ticket metadata
    Set-JuribaAppRApplicationOwner -AppId $appId -OwnerEmail $RequesterEmail

    # Watch packaging
    $result = Watch-JuribaAppRApplicationStatus -AppId $appId `
        -IntervalSeconds 300 -TimeoutMinutes 60

    if ($result.Status -eq 'ReadyForQualityReview') {
        # Publish to the target platform
        if ($TargetPlatform -eq 'Intune') {
            Invoke-JuribaAppRPublishIntune -Body @{
                applicationId = $appId
                packageType   = 4
            }
        }

        # Report success back to ServiceNow
        # Update-ServiceNowTicket -TicketId $TicketId -Status "Completed" `
        #     -Comment "Package published to $TargetPlatform. App ID: $appId"
    }
    else {
        # Report failure back to ServiceNow
        # Update-ServiceNowTicket -TicketId $TicketId -Status "Failed" `
        #     -Comment "Packaging failed with status: $($result.Status)"
    }
}
catch {
    # Update-ServiceNowTicket -TicketId $TicketId -Status "Error" `
    #     -Comment "Automation error: $($_.Exception.Message)"
    throw
}
finally {
    Disconnect-JuribaAppR
}

Replace the commented-out Update-ServiceNowTicket calls with your own ServiceNow API calls or PowerShell module. The same pattern applies to Jira, Freshservice, or any system that can invoke a PowerShell script via webhook or scheduled task.

6. Key Behaviors

These internal behaviors affect all of the workflows above. Understanding them helps when debugging unexpected results or customizing the automation flow.

Wrapping vs Repackaging

The module automatically determines whether to run VM-based repackaging or direct wrapping based on the output format bitmask configured in Default Settings:

Output Formats Enabled Mode from Value vmGroupId
MSI, MSIX, or MSIX App Attach (bitmask includes 1, 4, or 8) VM Repackaging 0 Configured VM group ID
IntuneWin and/or PSADT only (bitmask includes only 32 and/or 128) Direct Wrapping 4 -1 (no VM needed)

The output format bitmask values are: MSI=1, AppV=2, MSIX=4, MSIXAppAttach=8, IntuneWin=32, PSADT=128. When the bitmask contains any of MSI (1), MSIX (4), or MSIX App Attach (8), the module sets from=0 and assigns the configured VM group. When only IntuneWin (32) and/or PSADT (128) are enabled, it sets from=4 and vmGroupId=-1, bypassing VMs entirely.

Command Suggestion Priority

When creating an application, the server determines install and uninstall commands using three sources, evaluated in this priority order:

  1. Juriba Knowledge Base (source 3) -- curated commands from the KB, matched by file hash or application identity.
  2. Programmatic (source 1) -- detected from installer type, flags, and conventions (e.g., /S for NSIS, /VERYSILENT for Inno Setup).
  3. AI (source 2) -- AI-generated suggestions based on file analysis.

Within each source, previously successful commands are preferred. The sorting considers lastResult (positive means previously succeeded) and successRate (higher is better). This means the system learns over time: commands that have worked before for the same installer will be selected again.

Metadata Extraction Cascade

Application name, manufacturer, and version are resolved through a cascade of sources. Each step is tried in order; the first to return valid data wins:

  1. Server-side PE header extraction -- the server analyzes the uploaded binary's PE headers to extract ProductName, CompanyName, and ProductVersion.
  2. Client-side FileVersionInfo -- PowerShell's [System.Diagnostics.FileVersionInfo]::GetVersionInfo() extracts the same fields locally before upload. In the HTML portal, the proxy server performs this extraction.
  3. Knowledge Base metadata -- when using the KB workflow, the KB response provides the canonical name, vendor, and version.
  4. Filename fallback -- if no other source provides metadata, the filename is parsed as a last resort.

The New-JuribaAppRApplication cmdlet accepts -Name, -Manufacturer, and -Version as hints. These serve as fallbacks if server-side extraction does not return data.

Async Creation Pattern

Application creation is asynchronous. When you call New-JuribaAppRApplication, the server queues the work and returns immediately. The actual application ID is not available until the server finishes processing. This is why every workflow includes a polling loop:

# Poll until the server assigns an application ID
$state = Get-JuribaAppRApplicationCreationState -UploadId $upload.Uuid
$appId = $state.data.applicationId   # null until the server finishes

Typical resolution time is 5-30 seconds, but it can take longer under heavy load. All example scripts use a 5-minute timeout for this step. Once you have the application ID, you can begin polling the packaging status with Watch-JuribaAppRApplicationStatus.
